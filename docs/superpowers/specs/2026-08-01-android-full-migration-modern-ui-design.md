# ASTZB Android 全量功能迁移与现代化 UI 设计规格

日期：2026-08-01

状态：设计已确认，待用户审阅

目标平台：Android 13+（minSdk 33）

## 1. 背景与结论

`stzb_watcher` 的网页端已经具备抓包、战报、实时监控、地图、同盟、排行、考勤、统计和模拟器等完整能力。Android 端已经迁移了大部分本机抓包、解析和 SQLite 数据能力，但页面仍集中在超大 `DashboardActivity` 中，导航、状态、查询和渲染耦合，难以继续承载网页端全量功能。

本项目采用以下已确认方向：

- 以“实时战场动态”为默认首页；
- 视觉采用“现代深色战场指挥台”；
- 使用 Jetpack Compose 重做 Android 页面；
- 保留现有 VPN、SOCKS、协议解析、SQLite 和战斗模拟实现；
- 通过 Repository 和 ViewModel 逐步隔离现有大文件；
- 新旧界面阶段性并存，逐页替换，不中断现有抓包链路；
- 迁移网页端的能力和业务规则，不照搬桌面端表格布局。

## 2. 成功标准

完成后，用户无需 PC 或 Flask 服务即可在 Android 本机完成：

1. 启动和检查抓包链路；
2. 实时查看战斗、行军、攻城和系统动态；
3. 查询、筛选并查看完整战报；
4. 查看地图、州郡、排行榜、同盟和玩家统计；
5. 创建攻城任务并统计考勤；
6. 查看阵容统计并运行战斗模拟；
7. 导出数据库、报文和诊断信息；
8. 在加载、空数据、断流和解析失败时获得明确反馈。

UI 验收标准：

- 一级导航不超过 4 个；
- 进入 App 后一屏内看到抓包状态、关键指标和最新战场事件；
- 常用功能最多两次点击可达；
- 所有列表具备加载、空状态、错误和刷新反馈；
- 所有点击目标不小于 48dp；
- 正文对比度达到 WCAG AA，正文不小于 14sp；
- 页面滚动、实时更新和列表加载不出现明显卡顿；
- 不使用 Emoji 充当功能图标，不依赖颜色单独表达状态。

## 3. 范围与非目标

### 3.1 本次范围

- Android 页面框架和视觉系统；
- 网页端业务能力全量迁移；
- Android 数据访问接口拆分；
- 实时事件统一模型；
- 页面状态、导航、错误处理和测试体系；
- 旧 XML 页面渐进式退役。

### 3.2 非目标

- 不重写 VPN、tun2socks 或本机 SOCKS 捕获器；
- 不改变已验证的 STZB 包头与解码规则；
- 不要求重建现有 SQLite 数据；
- 不在 Android 内运行 Flask；
- 不对网页端做同步视觉改版；
- 不逐像素复制网页布局；
- 首轮不提供浅色主题，主题结构需保留未来扩展能力。

## 5. 核心页面设计

### 5.1 实时战场首页

页面从上到下由以下区域组成：

1. **运行状态栏**
   - 当前区服和角色；
   - 抓包状态圆点与文字；
   - 最后收到数据时间；
   - 诊断入口。
2. **关键指标横滑区**
   - 正在行军；
   - 活跃队伍；
   - 今日战斗；
   - 待关注攻城事件。
3. **实时动态 Feed**
   - 紧急、战斗、行军、攻城、系统五类事件；
   - 新事件轻微高亮一次，不强制抢占当前阅读位置；
   - 用户离开列表顶部时显示“有 N 条新动态”，点击后回到顶部；
   - 提供暂停/继续和类型筛选；
   - 点击事件进入对应战报、队伍、城池或诊断详情。
4. **重点目标**
   - 最近攻城目标；
   - 即将到达队伍；
   - 异常或断流提醒。
5. **地图态势摘要**
   - 展示命名城池、活跃地块和目标坐标摘要；
   - 点击进入地图页面。

实时动态不使用持续闪烁或自动滚动。Feed 默认保留最近 200 条 UI 事件，数据库仍保留完整记录。

### 5.2 战报列表与详情

战报列表由摘要栏、快速筛选和卡片列表组成。快速筛选包含今日、胜利、失败、攻城；完整筛选通过 Modal Bottom Sheet 展示玩家、同盟、类型、结果、地块和时间范围。

战报卡优先展示：结果、攻守双方、时间、地块、武勋/兵力指标和三武将摘要。战报详情使用独立页面，按“战果摘要—攻守阵容—武将战法—扩展指标—原始数据”渐进展开。原始 JSON 默认折叠，仅诊断时使用。

### 5.3 同盟中心

同盟首页展示成员数、总武勋、活跃度和最近攻城任务。成员、团数据、排行、考勤作为同一领域内的二级页面，而不是堆叠在一个超长页面。

成员页支持搜索、分组和排序；团数据支持今日、本周、全部时间；排行中心以玩家武勋、同盟武勋、个人势力和同盟势力四个标签组织；考勤页采用任务列表—任务详情—成员出勤的三级结构。

### 5.4 地图与监控

首阶段地图以可读的城池/地块列表、坐标搜索和态势摘要为主，不强行实现复杂自由缩放地图。行军监控按到达时间排序，展示玩家、同盟、起终点、剩余时间和最近战绩。到达时间变化使用文本更新，不使用持续进度动画。

### 5.5 更多与工具

工具按“分析工具、数据管理、系统状态”分组。抓包原始包、DB Sync 和诊断数据不出现在主导航。危险操作必须二次确认；导出完成后进入系统分享面板。

## 6. 视觉系统

### 6.1 风格

主题为“现代深色战场指挥台”：专业、克制、数据优先，带轻微游戏氛围但不游戏化堆砌。使用深蓝黑表面、琥珀金重点色、青绿色正常状态和朱红色告警。允许少量半透明分层，不使用大面积模糊、霓虹外发光或复杂动态背景。

### 6.2 颜色 token

| 语义 | 色值 | 用途 |
|---|---:|---|
| Background | `#0B1220` | 页面背景 |
| Surface | `#111B2E` | 导航和一级表面 |
| Surface High | `#18243A` | 卡片、弹层、选中区域 |
| Outline | `#2A3A55` | 描边和分隔线 |
| Primary | `#F59E0B` | 选中、关键行动、重要指标 |
| Secondary | `#818CF8` | 信息、链接、次级高亮 |
| Success | `#2DD4BF` | 正常、在线、成功 |
| Warning | `#FBBF24` | 需要关注、即将到达 |
| Error | `#F87171` | 异常、危险、失败 |
| Text Primary | `#F8FAFC` | 标题和主要数据 |
| Text Secondary | `#A8B3C7` | 描述和辅助字段 |

颜色只能通过 Material 3 `ColorScheme` 和业务语义 token 使用，页面中不散落硬编码颜色。

### 6.3 排版、尺寸与图标

- 系统无衬线字体，数字使用 tabular figures；
- 页面标题 24sp，区块标题 18sp，正文 14–16sp；
- KPI 数字 24–30sp；
- 4dp 基础网格，页面边距 16dp，卡片间距 12dp；
- 卡片圆角 16dp，按钮和标签圆角 10–14dp；
- 点击区域最小 48dp；
- 图标统一使用 Material Symbols Rounded；
- 状态同时使用图标、文字和颜色。

### 6.4 动效

- 点击反馈 80–120ms；
- 页面和弹层 180–250ms；
- 新事件背景高亮 300ms 后淡出；
- 列表只对首次出现内容使用轻量淡入；
- 尊重系统减少动画设置；
- 禁止持续发光、闪烁、无限旋转装饰和引发布局位移的动画。

## 7. 技术架构

### 7.1 分层

```text
capture / parser / database       现有底层，保持可用
              ↓
data repositories                按领域封装 SQLite 查询和写入
              ↓
domain models / use cases         统一业务模型与聚合规则
              ↓
ViewModel + UiState               页面状态和用户意图
              ↓
Jetpack Compose screens           纯 UI 渲染
```

### 7.2 模块目录

首轮仍使用单一 Gradle `app` 模块，先通过 package 建立 seam，避免一开始进行高风险多模块迁移：

```text
com.local.stzb
├── core/designsystem
├── core/navigation
├── core/ui
├── data/battle
├── data/battlefield
├── data/alliance
├── data/tools
├── domain/model
├── domain/usecase
├── feature/battlefield
├── feature/battles
├── feature/alliance
└── feature/tools
```

新代码使用正式包名 `com.local.stzb`；现有 `com.example.myapplication` 在迁移期间保留，通过适配器调用。完成页面替换后再统一 namespace，避免一次修改影响 Manifest、数据库和 native 桥接。

### 7.3 Repository

按领域建立少量深接口：

- `BattlefieldRepository`：实时事件、行军、攻城、地图与消息；
- `BattleRepository`：战报、详情、筛选、阵容和战场分析；
- `AllianceRepository`：成员、团数据、排行、任务和考勤；
- `ToolRepository`：玩家资料、公告、同步、导出与诊断。

Repository 对 UI 暴露 Kotlin `Flow`、分页结果和领域模型，不暴露 Cursor、表名或原始消息号。首批适配器内部调用现有 `LocalStzbRepository`，随后逐步把相关 SQL 移出 4,000 行大文件。

### 7.4 页面状态

每个页面使用不可变 `UiState`：

```kotlin
sealed interface LoadState<out T> {
    data object Loading : LoadState<Nothing>
    data class Content<T>(val value: T, val refreshing: Boolean) : LoadState<T>
    data class Empty(val message: String, val action: UiAction?) : LoadState<Nothing>
    data class Error(val message: String, val retryable: Boolean) : LoadState<Nothing>
}
```

ViewModel 接收用户 Intent，输出 `StateFlow<UiState>`。导航和 Snackbar 使用一次性事件通道，避免旋转屏幕或重新订阅时重复触发。

### 7.5 实时事件模型

PC/Android 原始消息统一转换为 UI 可理解的 `BattlefieldEvent`：

- `BattleStarted` / `BattleFinished`；
- `MarchStarted` / `MarchArriving`；
- `SiegeUpdated`；
- `ChatReceived`；
- `CaptureWarning` / `ParserWarning`；
- `SystemEvent`。

事件包含稳定 ID、时间、优先级、标题、摘要和目标链接。Compose 页面不判断 `5028`、`6314` 等原始消息号。

## 9. 错误处理与离线策略

- 数据库读取失败：保留页面结构，显示局部错误卡和重试；
- 抓包断流：不清空已有内容，顶部显示断流状态和诊断动作；
- 解析失败：写入诊断记录，不让单条坏包阻断 Feed；
- 无数据：说明原因并给出“启动抓包”“调整筛选”或“查看诊断”等动作；
- 实时刷新失败：退化为手动刷新；
- 导出失败：显示明确错误和目标路径，不只显示通用 Toast；
- 长耗时数据库查询运行在 IO dispatcher，可取消，页面离开后不得继续回写旧状态。

## 12. 风险与控制

- **范围过大**：按四批交付，每批形成可用闭环；
- **Compose 与旧 UI 并存复杂**：统一由单一导航入口管理，旧页面只作为明确的兼容目标；
- **数据库大文件继续膨胀**：所有新页面只通过领域 Repository 访问数据；
- **真机报文不一致**：先补黄金样本，再宣称功能迁移完成；
- **实时刷新卡顿**：事件限流、稳定 key、LazyColumn 和后台聚合；
- **现代视觉影响可读性**：限制透明度和动效，文本对比度优先于装饰效果；
- **已有用户数据升级**：不破坏现有 schema，所有新增迁移可重复执行。

## 13. 完成定义

项目完成必须同时满足：

- 迁移矩阵中所有能力完成并通过验收；
- App 首屏为实时战场动态；
- 四入口导航和现代深色设计系统覆盖全部新页面；
- `DashboardActivity` 不再承担业务页面渲染；
