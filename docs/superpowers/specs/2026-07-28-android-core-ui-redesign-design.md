# ASTZB Android 核心 UI 重设计规格

日期：2026-07-28
状态：已完成设计确认，待规格审阅

## 1. 背景

ASTZB Android 已完成本机抓包、协议解析、SQLite 入库及主要业务能力迁移，但核心页面仍保留较强的 PoC 特征：

- 页面入口集中在侧边栏，核心功能层级不够清晰；
- 部分页面以大段文本或密集按钮呈现，缺少移动端信息层级；
- 颜色、间距、圆角、状态和交互反馈尚未形成统一设计系统；
- `DashboardActivity` 同时承担导航、页面状态和大量渲染逻辑，继续直接叠加 UI 会增加维护成本。

本轮目标是重做五个高频页面，并建立可继续复用的 Android UI 基础，而不是迁移 UI 技术栈或重写业务层。

## 2. 已确认决策

- 改造范围：`首页 / 战报列表 / 战报详情 / 战场监控 / 排行中心`。
- 风格：现代数据终端。
- 颜色模式：本轮统一采用深色模式。
- 导航：底部五个主入口，首页提供更多快捷入口。
- 技术栈：保留 XML + Material Components，不迁移 Jetpack Compose。
- 改造深度：核心体验重做，而非单纯换肤或完整架构迁移。
- 数据边界：不修改抓包、解析、SQLite 表结构和现有业务数据接口。

## 3. 目标与非目标

### 3.1 目标

1. 用户进入 App 后能立即判断本机数据链路是否正常。
2. 五个核心页面形成一致、专业、可读的数据终端体验。
3. 高频入口单手可达，低频入口仍可快速访问。
4. 战报、监控和排行先展示结论，再按需展开细节。
5. 页面具备完整的加载、空数据、失败、刷新和禁用状态。
6. 建立可复用的主题 token、卡片、状态标签和 UI 映射层。
7. 保持现有数据功能和抓包链路不回归。

### 3.2 非目标

- 不迁移 Jetpack Compose。
- 不重写 `LocalStzbRepository`。
- 不修改数据库 schema。
- 不修改报文解析逻辑。
- 不在本轮产品化全部“更多”页面。
- 不实现复杂地图交互。
- 不同时维护完整浅色主题。
- 不追求与 Web Dashboard 像素级一致。

## 4. 信息架构与导航

### 4.1 底部主导航

底部固定五个入口：

1. 首页
2. 战报
3. 监控
4. 排行
5. 更多

约束：

- 每个入口同时显示统一风格的 Material 图标与文字；
- 点击区域不小于 48dp；
- 当前入口使用青蓝色强调、背景胶囊或顶部指示条；
- 切换入口时保留列表滚动、筛选条件和页面内选项；
- 底部安全区必须被正确处理，列表内容不能被导航遮挡；
- 系统返回键优先关闭弹层或返回页面层级，不应在一级入口间制造不可预测跳转。

### 4.2 首页快捷入口

首页提供六个快捷入口：

- 团数据
- 同盟成员
- 城池地图
- 攻城考勤
- 武将阵容
- 模拟器

快捷入口采用两列或三列自适应宫格。低频调试、抓包、公告、同步记录等能力统一进入“更多”页面。

### 4.3 侧边栏迁移

现有侧边栏不再承担五个核心页面的主导航。其余入口逐步迁移到“更多”页面；本轮允许保留兼容实现，但不应继续新增侧边栏主入口。

## 5. 视觉系统

### 5.1 设计原则

- 深色但不使用纯黑，避免 OLED 拖影和廉价荧光屏观感；
- 高密度但可读，关键结论优先；
- 层级主要依靠表面色、边框、字号和间距，不依赖大面积阴影；
- 青蓝用于导航、实时和信息状态，琥珀用于关键行动与重点提示；
- 红绿状态必须同时带文字或图标，不把颜色作为唯一信息来源；
- 不使用 Emoji 作为结构性图标。

### 5.2 语义颜色 token

| Token | 色值 | 用途 |
|---|---:|---|
| `colorBackground` | `#08111F` | 页面背景 |
| `colorSurface` | `#0F1B2D` | 一级表面、导航和顶部栏 |
| `colorSurfaceRaised` | `#142238` | 卡片、弹层和选中区域 |
| `colorBorder` | `#263750` | 分隔线和卡片描边 |
| `colorTextPrimary` | `#F4F7FB` | 主标题和主要数据 |
| `colorTextSecondary` | `#9AAAC0` | 描述和辅助字段 |
| `colorPrimary` | `#38BDF8` | 当前导航、实时状态、主要链接 |
| `colorAccent` | `#F59E0B` | 关键行动和重点指标 |
| `colorSuccess` | `#22C55E` | 成功、正常、胜利 |
| `colorDanger` | `#F05252` | 失败、异常、危险 |
| `colorWarning` | `#FBBF24` | 即将到达、需要关注 |
| `colorScrim` | `#99000000` | 抽屉和弹层遮罩 |

所有页面必须引用语义 token，不能在页面布局中散落硬编码业务颜色。

### 5.3 排版

- 使用 Android 系统字体，避免增加网络或字体包依赖；
- 页面标题：22sp–24sp，Semibold/Bold；
- 区块标题：18sp，Semibold；
- 正文与列表主信息：至少 16sp；
- 辅助信息：13sp–14sp；
- KPI 数字：24sp–30sp，Bold；
- 坐标、队伍 ID、战报 ID 等数据字段使用等宽字形；
- 支持系统字体放大，最大字体下关键数据不能被裁剪。

### 5.4 间距、圆角与尺寸

- 基础网格：4dp；
- 页面水平边距：16dp；
- 卡片内边距：16dp；
- 卡片间距：12dp；
- 区块间距：24dp；
- 卡片圆角：14dp；
- 标签圆角：8dp 或胶囊形；
- 按钮最小高度：48dp；
- 图标规范尺寸：20dp、24dp、28dp；
- 相邻点击区域至少保留 8dp 间隔。

### 5.5 动效

- 点击反馈在 80–150ms 内出现；
- 页面、筛选和状态切换为 150–250ms；
- 进入使用 ease-out，退出使用 ease-in；
- 不使用持续装饰性循环动画；
- 实时事件只做一次轻微背景高亮，不改变布局边界；
- 开启“减少动画”时移除非必要位移和渐变动画。

## 6. 通用 UI 模块

### 6.1 `AppTheme`

统一提供：

- 语义颜色；
- 字号层级；
- 间距和圆角；
- 卡片、按钮、输入框、标签和弹层样式；
- 成功、警告、危险和实时状态样式。

### 6.2 `MainNavigation`

职责：

- 管理五个一级入口；
- 保存各入口页面状态；
- 处理底部安全区；
- 保持 Android 返回行为可预测。

### 6.3 `DashboardCards`

包含：

- KPI 卡；
- 快捷入口卡；
- 链路状态节点；
- 最近动态卡；
- 加载骨架；
- 空状态；
- 页面内错误卡。

### 6.4 UI Mapper

新增纯 Kotlin UI 映射层：

- `BattleUiMapper`：数据库模型 → 战报列表卡和详情视图数据；
- `MonitorUiMapper`：监控记录 → 状态、时间、坐标和倒计时视图数据；
- `RankingUiMapper`：排行数据 → 名次、主指标、辅助指标和高亮状态。

Mapper 不持有 Android `Context`，不访问 SQLite，不操作 View，便于纯单元测试。

## 7. 页面规格

### 7.1 首页

从上到下：

1. 顶部状态栏
   - 产品名称；
   - 抓包总状态；
   - 最后更新时间；
   - 刷新动作。
2. 核心指标
   - 今日战报；
   - 活跃队伍；
   - 同盟成员；
   - 监控事件；
   - 手机端两列排列。
3. 实时链路
   - VPN；
   - SOCKS5；
   - 解析器；
   - SQLite；
   - 每个节点显示正常、警告或异常；
   - 节点异常时给出可执行说明。
4. 快捷入口宫格
   - 团数据、同盟成员、城池地图、攻城考勤、武将阵容、模拟器。
5. 最近动态
   - 最近 3–5 条战报或监控事件；
   - 点击进入对应页面或详情。

首页首次启动无数据时，不显示空白 KPI；应解释需要开启抓包，并提供明确主行动。

### 7.2 战报列表

顶部区域：

- 页面标题；
- 当前结果数量；
- 搜索按钮；
- 筛选按钮。

快速筛选：

- 全部；
- 胜利；
- 失败；
- 攻城；
- 今日。

高级筛选进入底部弹层，承载：

- 玩家；
- 同盟；
- 战斗类型；
- 结果；
- 地块 wid；
- 开始时间；
- 结束时间；
- 重置和应用动作。

战报卡片优先级：

1. 结果；
2. 攻守双方；
3. 时间与地块；
4. 武勋、兵力或其他主指标；
5. 武将阵容摘要。

状态表达：

- 左侧状态条；
- 结果文字；
- 结果图标；
- 红绿只是辅助。

列表必须支持：

- 下拉刷新；
- 加载骨架；
- 空结果状态；
- 加载失败重试；
- 当前筛选摘要；
- 返回后恢复滚动位置。

### 7.3 战报详情

页面结构：

1. 结果摘要
   - 结果；
   - 时间；
   - 地块；
   - 战斗类型。
2. 攻守双方
   - 对称布局；
   - 玩家和同盟；
   - 中间 `VS`；
   - 初始与剩余兵力。
3. 武将阵容
   - 每方三名武将；
   - 名称、等级、兵力、战法；
   - 空位有明确占位。
4. 战果指标
   - 武勋；
   - 势力变化；
   - 伤兵；
   - 其他已有关键字段。
5. 扩展信息
   - 天气；
   - 夜战；
   - 驻守；
   - NPC；
   - 默认折叠。
6. 调试信息
   - 原始 JSON；
   - 默认折叠；
   - 不参与主要阅读流。

若只存在 2100 通知而没有完整战报，页面应显示“通知级数据”状态，并隐藏无法提供的模块，而不是显示大量空字段。

### 7.4 战场监控

顶部区域：

- 实时状态；
- 最后刷新时间；
- 暂停/继续；
- 筛选入口。

主体为时间线 Feed。每条事件展示：

- 队伍；
- 玩家；
- 同盟；
- 起点；
- 终点；
- 当前坐标；
- 到达时间或倒计时；
- 状态标签。

状态分类：

- 行军中；
- 即将到达；
- 交战中；
- 已结束；
- 数据不完整。

行为：

- 新事件轻微高亮；
- 用户不在列表顶部时，不自动抢走滚动位置；
- 可以手动跳到最新；
- 坐标和队伍 ID 支持复制；
- 暂停只暂停 UI 刷新，不关闭底层抓包；
- 搜索和过滤统一放入底部弹层。

### 7.5 排行中心

顶部分段切换：

- 玩家武勋；
- 同盟武勋；
- 玩家势力。

结构：

- 前三名使用紧凑领奖台摘要；
- 其余使用统一榜单行；
- 每行包含名次、名称、核心值和辅助指标；
- 当前用户或当前同盟使用描边和“当前”标签高亮；
- 支持时间范围和同盟筛选；
- 排名变化同时使用箭头、文字和数值。

当样本量不足时，页面必须显示统计口径说明。

## 8. 数据流与状态

页面数据流保持单向：

```text
LocalStzbRepository
  -> 业务数据模型
  -> 纯 Kotlin UI Mapper
  -> 页面视图状态
  -> XML View / Adapter
```

页面视图状态至少覆盖：

- `InitialLoading`
- `Content`
- `Refreshing`
- `Empty`
- `Error`

刷新时保留旧内容，顶部或局部展示小型进度状态，不清空整个页面。

## 9. 错误与空状态

### 9.1 首次加载

显示与最终布局一致的骨架结构，避免页面跳动。

### 9.2 无数据

空状态必须说明原因，并根据场景提供动作：

- 尚未开启抓包 → “开启抓包”；
- 当前筛选无结果 → “清除筛选”；
- 数据库为空 → “刷新数据”；
- 监控已暂停 → “继续监控”。

### 9.3 查询失败

使用页面内错误卡，包含：

- 简短错误说明；
- 重试动作；
- 必要时提供诊断入口。

非阻断错误不连续弹 Toast。

### 9.4 链路异常

首页实时链路需要指出具体故障节点，而不是只显示“连接失败”。

## 10. 可访问性

- Android 点击区域不小于 48×48dp；
- 主文字对背景对比度不低于 4.5:1；
- 次文字和大型图标对比度不低于 3:1；
- 所有图标按钮具有可读的无障碍标签；
- TalkBack 焦点顺序与视觉顺序一致；
- 状态不只依赖颜色；
- 最大系统字体下关键字段不被裁剪；
- 固定导航、顶部栏和弹层尊重系统安全区；
- 弹层提供清晰关闭动作；
- 自定义滑动不与系统返回和列表滚动冲突。

## 11. 测试与验收

### 11.1 自动化

- 保持现有 Android 单元测试通过；
- 为三个 UI Mapper 增加纯 Kotlin 单元测试；
- 覆盖胜负、未知结果、空字段、超长名称、缺失阵容和排行并列；
- 对主题 token 和关键资源执行资源编译检查。

### 11.2 手工设备矩阵

- 小屏手机；
- 普通尺寸手机；
- 大屏手机或平板；
- 竖屏和横屏；
- 默认字体和最大系统字体；
- 正常动画和减少动画；
- 手势导航和三键导航。

### 11.3 核心验收条件

- 五个底部入口均可访问，且列表内容不被底栏遮挡；
- 首页能识别并展示 VPN、SOCKS5、解析器和数据库状态；
- 战报高级筛选不常驻占用页面空间；
- 战报详情不再以原始文本作为主体；
- 监控新事件不会强制改变用户滚动位置；
- 排行前三名和普通排行层级清晰；
- 返回页面后保留筛选条件和滚动位置；
- 所有主要交互具有点击反馈；
- 深色页面不存在不可读的低对比文字；
- 抓包、解析、数据库写入和已有业务查询不因 UI 重做发生行为变化。

## 12. 实施顺序约束

后续实施计划应遵循以下依赖顺序：

1. 主题 token 与通用样式；
2. 底部导航和页面状态容器；
3. 通用卡片、标签、加载、空状态和错误状态；
4. 首页；
5. 战报列表；
6. 战报详情；
7. 战场监控；
8. 排行中心；
9. 可访问性与多尺寸校验；
10. 回归测试。

页面改造必须小步提交，不能把五个页面和底层业务改动混入同一个提交。
