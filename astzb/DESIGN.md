# ASTZB App 设计文档

本文件不是单纯的视觉说明，而是 `stzb_watcher` 整体项目向 `astzb/` Android App 迁移时的产品设计与界面设计总纲。

项目全貌需要这样理解：

- 外围主项目是网页端战场平台：抓包、解析、写库、Web 仪表盘、实时监控、战报分析、团队统计、地图与考勤
- `astzb/` 是要生成的 Android App 项目：目标不是做一个全新产品，而是把网页端的核心能力直接迁移到手机端，并且去掉对 PC Flask 服务的依赖
- 因此 App 的设计目标不是“重新发明一套功能”，而是把 Web 端已经验证过的高价值能力，按照移动端使用方式重新组织

这个文档的核心作用是：

1. 重新梳理整个仓库的产品结构
2. 明确网页端能力与 App 端能力的一一映射
3. 定义 App 的信息架构、页面结构、视觉方向与交互规则
4. 约束后续任何人或 coding agent 在 `astzb/` 中继续生成页面时，不偏离“网页能力直迁”的主线

---

## 0.1 UI/UX Pro Max 集成说明

本项目已安装 UI/UX Pro Max，并生成了以下设计系统文件：

- `.claude/skills/ui-ux-pro-max/`
- `design-system/astzb/MASTER.md`

这些文件可以作为本设计文档的补充参考，但不能直接照搬。原因是该工具生成的默认推荐偏向通用 analytics dashboard 和 App Store 风格落地页，而 `astzb` 的实际目标是：

- 网页端战场平台能力迁移
- 本机抓包与本机数据分析
- 深色战场指挥台 + 浅色工具页的双场景 App

因此，本项目对 UIPro 的使用原则是：

### 采用的部分

- `Data-Dense Dashboard` 作为分析页和监控页的主要设计方向
- 4px spacing 基线与 token 化间距
- 16px 以上移动端正文字号要求
- 150ms - 300ms 的微交互动效区间
- 焦点态、对比度、可访问性、reduced-motion 等硬规则
- 过滤、排序、hover/tap 反馈、loading state 这些高价值交互建议

### 不直接采用的部分

- `App Store Style Landing` 作为产品主模式
- 通用 BI 看板的浅色蓝色系全局方案
- 过于 Web 导向的 landing page 结构

结论：

UIPro 在本项目中扮演的是“设计系统增强器”，不是最终设计答案。最终以本文件为准。

## 1. 整体项目结构认知

### 1.1 外围网页端项目是什么

外围主项目 `stzb_watcher` 本质上是《率土之滨》战场实时监控与数据分析平台，当前主要形态是：

- 抓包与解析：`scrapy_v2.py`
- 实时写库：`realtime_writer.py`
- Flask API：`api_server.py`
- 静态 Dashboard：`static/dashboard.html` + `static/app1.js` + `static/app2.js`

网页端已经沉淀出的成熟能力包括：

- 全部战报
- 战报详情
- 团数据
- 战场分析
- 武将阵容
- 分组武勋
- 同盟成员
- 攻城考勤
- 战场态势
- 战场消息
- 城池地图
- 排行榜
- 账号档案切换
- 实时事件流
- 战斗模拟器

网页端相当于现阶段的“产品全量能力母体”。

---

### 1.2 astzb App 是什么

`astzb/` 不是一个普通配套客户端，而是未来真正独立运行的移动端版本。它的目标是：

- 在 Android 本机完成抓包
- 在 Android 本机完成 STZB 包识别与解析
- 在 Android 本机完成 SQLite 入库
- 在 Android 本机完成数据展示与分析
- 最终把网页端核心功能迁移到 App 端

因此 `astzb` 的正确定位是：

**网页端战场平台的移动端本地化迁移版本。**

不是 PC 的遥控器，不是只看日志的工具壳，也不是只做抓包验证的工程页。

同时要特别说明一件事：

- App 需要尽量复刻网页端的信息结构、模块组织、展示节奏和数据表达方式
- 但不必继承网页端当前那套具体配色

也就是说，App 要继承的是网页端的“展示逻辑”和“信息密度能力”，而不是简单做一套移动版换壳。

---

### 1.3 当前 astzb 已经具备什么基础

根据 `astzb/README.md` 和现有 `DashboardActivity`，App 端已经具备：

- 本机抓包桥接
- 本机 STZB 流解析
- 本机 SQLite 数据层
- 完整战报 `10/92` 解析入库
- 2100 战报通知 / 聊天解析
- 5028 行军监控解析
- 700 排行相关入库与展示
- 103 同盟成员入库与展示
- 5026 地图格子入库与展示
- 510 玩家统计、780 公告、6243 战区玩家、90005 同步表等通用业务记录入库
- 本机导出能力
- 本机战报详情查看
- 本机战斗模拟资源加载

也就是说：App 端已经不是空白，而是已经具备“承接网页功能迁移”的数据基础。

## 2. App 的产品目标

App 的设计目标必须围绕“网页能力直迁”定义，而不是围绕当前 PoC 页面定义。

### 2.1 一级目标

把网页端的核心高频能力迁移到 Android 本机，形成真正可用的移动端战场数据终端。

### 2.2 二级目标

- 用户在手机上直接完成抓包、解析、查看、分析
- 用户在手机上快速查看战场核心信息，不必先开电脑
- 用户在移动端做“查看、监控、筛选、判断、导出”的高频动作
- 用户在移动端获得与网页端一致的数据心智，而不是另一套完全不同的产品逻辑

### 2.3 非目标

当前阶段不把 App 设计成：

- 社交型产品
- 泛资讯产品
- 轻娱乐游戏伴侣
- 纯原始调试面板

App 是专业工具，是移动战场终端。

## 4. App 的信息架构

App 不能直接把 Web 的全部 tab 原样搬成一条超长横向导航。移动端必须重组。

推荐采用 **一级侧栏导航 + 二级子标签页切换** 的结构。

### 4.1 一级导航

一级导航建议分为 7 个主域：

1. 首页
2. 战场
3. 分析
4. 战报
5. 组织
6. 工具
7. 扩展

---

#### 首页

承载：

- 本机运行状态
- 数据概览
- 最近战场摘要
- 快捷入口

#### 战场

- 战场消息

- 团数据
- 战场分析
- 武将阵容
- 分组武勋
- 武勋统计
- 势力值

#### 组织

承载：

### 4.3 二级导航组织

每个一级页内再做模块切换，而不是全局放几十个 tab。

例如：

- 首页：总览 / 最近动态 / 快捷入口
- 战报：全部战报 / 玩家队伍 / 队伍统计 / 玩家战绩
- 战场：战场监控 / 13A2 队伍索引 / 战场消息 / 城池地图 / 州郡分布 / 战区玩家
- 分析：排行榜 / 战场分析 / 团数据 / 武将阵容 / 分组武勋 / 武勋统计 / 势力值
- 组织：同盟成员 / 同盟成员队伍 / 攻城考勤 / 打城排表
- 工具：抓包桥接 / 数据同步 / 导出诊断 / 原始包检查
- 扩展：战斗模拟 / 古代中国地图

---

### 4.4 为什么必须用侧栏 + 子标签

网页端当前使用的是横向长 tab，这在桌面端可接受，但在移动端会有明显问题：

- 标签过多，无法形成主次
- 用户难以建立功能域认知
- 高频页与低频页被放在同一层级
- 很难把“业务页”和“工具页”清楚拆开

改成侧栏 + 子标签页之后：

- 一级侧栏负责表达功能域
- 二级子标签负责表达具体模块
- 结构上更接近真正的 App
- 后续页面扩展时不会再次变成横向 tab 堆积

## 5. 关键页面设计

### 5.1 首页

首页必须回答四个问题：

1. 本机抓包链路是否正常
2. 本机数据库里当前有什么数据
3. 用户最应该先看哪个入口
4. 最近有没有值得注意的战场变化

首页建议结构：

- Hero 区：App 名称、当前角色、区服、状态
- 状态卡：抓包状态 / 桥接状态 / 数据库状态 / 最近更新时间
- 数据摘要卡：战报、成员、地图、行军、消息数量
- 快捷入口：全部战报、行军监控、排行榜、同盟成员
- 最近动态：最近战报 / 最近公告 / 最近监控变更
- 工具快捷区：启动抓包、导出数据库、导出诊断

首页不是日志堆放页。

---

### 5.2 战报页

战报页是 App 核心页，必须优先做好。

结构建议：

- 顶部标题 + 数据源说明
- 筛选摘要条
- 筛选面板
- 统计摘要：总条数 / 完整战报 / 通知兜底 / 当前条件
- 战报列表

每条战报列表项至少包含：

- 时间
- 结果 badge
- 类型 badge
- 攻方
- 守方
- 武勋 / wid / 来源

点击后进入详情页。

---

### 5.3 战报详情页

战报详情页不能只是一大段文本。

建议分块：

- 概览卡：时间、结果、类型、wid、来源
- 攻方卡
- 守方卡
- 武将阵容卡
- 战法卡
- 战果指标卡
- 调试数据折叠区

首屏必须先给结论，再给明细。

---

### 5.4 行军监控页

这是 Web 端很有特色的能力，App 端应重点保留。

页面结构建议：

- 顶部状态摘要：队伍数、最新时间、更新时间、监控状态
- 搜索 / 筛选：玩家、同盟、队伍 ID、坐标
- 队伍流式列表

每条监控卡片建议展示：

- 队伍 ID
- 玩家 / 同盟
- 出发 / 目标 / 当前坐标
- 到达时间 / 剩余时间
- 阵容胜率摘要
- 最近几场战绩
- 更克制阵容 / 更被克制阵容
- 武将与战法

这个页面应采用“深色战场控制台”视觉。

---

### 5.5 排行中心

排行榜不要拆成多个孤立页面，应该做成一个中心页。

内部切换维度：

- 玩家武勋
- 同盟武勋
- 玩家势力
- 同盟排行
- 个人势力排行

页面元素：

- 维度切换
- Top3 强调区

### 5.14 网页端展示形式的复刻原则

App 需要复刻网页端的，不是颜色，而是以下这些“展示形式”：

#### 必须继承的部分

- 顶部筛选条 + 刷新按钮
- 统计卡片 + 主内容区的节奏
- 表格 / 列表 / 分布条形图的组合关系
- 深度页面先摘要、后细节
- 实时监控页的 feed 流结构
- 分析页的卡片 + 图表 + 表格混排
- 详情页的分组信息展示方式

#### 可以重做的部分

- 全局配色
- 字体搭配
- 卡片圆角大小
- 视觉质感方向
- 主强调色与辅助色

结论：

App 应“复刻网页的内容组织和展示逻辑”，但允许建立更适合移动端的新视觉体系。

## 6. App 的视觉方向

### 6.1 总体风格

App 不是通用企业后台，也不是赛博炫技工具。它应形成统一的“率土战场指挥终端”品牌感。

视觉关键词：

- 沉稳
- 专业
- 高信息密度
- 带战场氛围
- 可长时间阅读

---

### 6.2 双场景视觉系统

根据当前项目实际情况，App 应采用双场景视觉，而不是全站单一种风格。

#### 场景 A：首页 / 工具页

适合：

- 首页
- 抓包工具
- 导出工具
- 诊断页

风格：

- 浅色玻璃态
- 柔和渐变背景
- 大圆角卡片
- 更强调入口和状态

#### 场景 B：战场 / 分析页

适合：

- 战报
- 行军监控
- 排行
- 团数据
- 地图
- 公告与消息

风格：

- 深色指挥台
- 金色 / 灰蓝点缀
- 高密度信息面板
- 更强调数据与层级

禁止新增第三套主题语言。

---

### 6.2.1 不继承网页配色的设计原则

虽然网页端现在是“深蓝黑 + 金色”的战场风格，但 App 不要求完全继承它的色值。可以在保证气质一致的前提下，重新定义更适合移动端长期使用的颜色系统。

App 的新视觉体系应满足：

- 仍然有战术终端气质
- 仍然适合高密度数据阅读
- 仍然适合监控、排行、战报、地图等页面
- 但比网页端更精致、更统一、更适合手机持续浏览

这意味着：

- 可以不沿用网页的金色标题和蓝黑底色原值
- 可以换成新的主强调色与中性色体系
- 但不能把产品做成普通 SaaS 后台或通用 BI 工具

---

### 6.2.2 App 新配色方向建议

如果不沿用网页配色，推荐 App 采用“深色中性基底 + 单一高识别强调色 + 少量语义色”的方式。

推荐方向：

#### 方案 A：石墨黑 + 琥珀金

- 背景：石墨黑 / 墨灰
- 面板：深灰蓝或枪灰
- 强调色：琥珀金
- 优点：保留战场和策略感，和网页气质连续

#### 方案 B：深空灰 + 冰青蓝

- 背景：深空灰
- 面板：冷灰蓝
- 强调色：冰青蓝
- 优点：更现代、更移动端、科技感更强

#### 方案 C：煤黑 + 铜橙

- 背景：煤黑
- 面板：深棕灰
- 强调色：铜橙
- 优点：更有战争沙盘和指挥台气质

默认建议：

- 首页 / 工具页可更柔和、更有质感
- 战场 / 分析 / 战报页保持深色高密度体系

### 6.3 颜色角色

#### 浅色工具体系

- 背景：暖白到冷白渐变
- 主强调：玫红 / 品牌色
- 辅助强调：青蓝
- 卡片：半透明白
- 正文：深灰

#### 深色战场体系

- 背景：深蓝黑
- 面板：深色卡片
- 边框：冷灰蓝
- 强调：金色
- 正文：浅米灰
- 次级文字：灰蓝

#### 语义色

- 成功：青绿
- 警告：金黄 / 琥珀
- 失败：暗红
- 信息：蓝色

语义色只能表达状态，不要滥用为主题色。

另外补充：

- App 配色以“角色清晰”和“长期阅读舒适”为第一原则
- 不以“网页复刻原色”为第一原则

---

### 6.4 UIPro 补充后的设计 token

在不破坏项目现有气质的前提下，推荐把颜色和间距逐步收敛为 token 思维。

#### 间距 token

- `space-xs = 4dp`
- `space-sm = 8dp`
- `space-md = 16dp`
- `space-lg = 24dp`
- `space-xl = 32dp`
- `space-2xl = 48dp`

适用原则：

- 行内元素：4 / 8
- 卡片内边距：16 / 24
- 页面分段：24 / 32
- 大区块间距：32 / 48

#### 阴影与层级 token

- `shadow-sm`：轻量抬升，用于浅色工具卡片
- `shadow-md`：标准卡片阴影
- `shadow-lg`：弹层、重要卡片
- 深色战场页优先依靠边框和明暗层级，不依赖夸张阴影

#### 圆角 token

- `radius-sm = 8dp`
- `radius-md = 12dp`
- `radius-lg = 16dp`
- `radius-xl = 24dp`
- `radius-hero = 28dp - 32dp`

建议：

- 工具页和首页多用 `lg/xl/hero`
- 战场页多用 `sm/md`

#### 字体 token

- 页面标题：24sp - 30sp
- 区块标题：18sp - 22sp
- 小节标题：15sp - 17sp
- 正文：16sp 起步优先，最低不低于 14sp
- 次级信息：12sp - 13sp
- 数据数字：24sp - 32sp

说明：

- UIPro 推荐的数据型字体气质是对的，但 Android 端不必强行套 `Fira Code / Fira Sans`
- 可借鉴其“技术感 + 精确感”方向，只在数字、坐标、时间、ID 等场景局部引入等宽风格
- 大段正文和业务文案仍应优先选择更适合中文阅读的系统字体体验

## 7. 设计原则

### 7.1 功能迁移优先于视觉炫技

App 的第一原则不是好看，而是准确承接网页端高价值能力。

### 7.2 信息层级必须比网页更清楚

因为手机屏幕更小，所以要比网页更严格地控制层级：

- 标题层
- 状态层
- 操作层
- 内容层

### 7.3 列表是第一公民

这个产品的大量价值来自列表浏览。所有列表都必须可扫读、可筛选、可进入详情。

### 7.4 状态反馈必须显式

启动、刷新、导出、解析、错误、空态都要有清晰反馈，不能只躲在日志里。

### 7.5 先摘要，后细节

所有分析页、详情页、监控页都要先给结论，再给展开信息。

### 7.5.1 页面结构比视觉复刻更重要

如果“结构复刻”和“颜色复刻”出现冲突，优先保留结构。

例如：

- 保留网页的筛选 + 卡片 + 表格 + 分布图关系
- 但可以替换网页的颜色体系

这条原则适用于所有从网页迁移到 App 的页面。

### 7.6 过滤能力是硬要求

UIPro 给出的 `No filtering` anti-pattern 与本项目高度一致。对于 `astzb` 这种战场数据终端，以下页面默认必须支持筛选或切换：

- 战报
- 排行
- 团数据
- 成员
- 行军监控
- 公告 / 消息 / 同步记录

如果某个页面暂时无法提供复杂筛选，也必须至少提供：

- 时间范围
- 关键词搜索
- 维度切换

### 7.7 交互密度高，但不能牺牲可点击性

UIPro 强调 `touch-target-size` 和明确点击反馈，这对 App 很关键。

要求：

- 可点击区域优先满足 44dp 以上触达
- 复杂卡片内的关键点击点必须有明确视觉提示
- 不要把主操作做成过小文字链接

### 7.8 一切状态变化都要可感知

UIPro 推荐 loading button、error feedback、smooth transitions，这些都应纳入 App 规则：

- 刷新时要有 loading 态
- 导出时要有进行中与完成态
- 筛选应用后要有结果反馈
- 错误提示要贴近出错动作
- 状态切换要有轻量过渡，而不是瞬间跳变

---

## 8. 列表与详情的统一规范

### 8.1 列表项结构

每个列表项尽量遵循三层：

- 主信息：对象名 / 结论
- 次信息：时间 / 来源 / 关系
- 状态信息：结果 / 指标 / 标签

### 8.2 详情页结构

详情页统一遵循：

1. 标题与返回
2. 核心摘要卡
3. 分组内容块
4. 原始数据折叠区

### 8.3 空态 / 错误态 / 加载态

每个业务页必须有：

- 空态：告诉用户为什么空，以及下一步做什么
- 错误态：告诉用户哪里失败，以及怎么处理
- 加载态：不要只放一句“加载中...”长期无反馈

### 8.4 表格与图表的取舍

UIPro 的 `Data-Dense Dashboard` 很适合这个项目，但移动端不能机械复制 PC 表格。

规则：

- 手机上优先卡片化列表，而不是宽表格
- 图表只显示最关键结论，不把网页端整屏图表照搬
- 对需要横向信息对比的数据，用分段指标卡或可折叠明细替代表格
- 如必须使用表格，应支持横滑且保证表头固定、字段优先级清晰

从产品价值和当前基础来看，App 迁移优先级建议如下：

### 第一优先级

## 9.1 基于 UIPro 的页面质量基线

后续任何页面在交付前，都至少满足以下检查项：

- 没有把主状态埋在长日志里
- 所有关键操作都有明确点击态与 loading 态
- 所有交互元素有可见焦点态或按压反馈
- 文本对比度足够，特别是深色页面
- 移动端正文可读，默认不小于 14sp，优先 16sp
- 不出现横向溢出导致的意外滚动
- 不使用 emoji 充当主要图标
- 图标风格统一
- 动效控制在 150ms - 300ms，并支持 reduced-motion 降级
- 不因 hover / 动效造成布局抖动

这组规则比单纯“好不好看”更重要。

## 10. 给后续设计与生成的明确约束

以后在 `astzb/` 中设计或生成页面时，必须遵守：

- 默认从网页端能力映射出发，不要重新发明功能域
- 不要把 Web 的几十个 tab 机械搬到手机上
- 不要把所有内容塞进一个长 `TextView`
- 不要只做抓包工具壳，而忽略战场分析能力
- 不要做成通用后台模板风
- 不要做廉价霓虹赛博风
- 不要新增第三套完全不同的主题系统
- 不要照搬 `design-system/astzb/MASTER.md` 里的 App Store 落地页结构
- 不要因为追求数据密度而取消筛选、状态反馈和可读性

新增页面必须回答三个问题：

1. 它对应网页端哪个能力
2. 它在 App 一级导航中属于哪个主域
3. 它在移动端最适合用什么结构承载

如果这三个问题回答不清，就不应该直接开始画 UI。

## 10.1 给 coding agent 的执行流程

以后如果使用 AI 继续生成 `astzb` 页面，推荐遵循下面的顺序：

1. 先看本文件，确认该页面属于哪个功能域
2. 再看 `design-system/astzb/MASTER.md`，吸收其中可复用的设计系统规则
3. 如果未来存在 `design-system/astzb/pages/<page>.md`，则页面级规则优先
4. 输出页面时优先保证：信息层级、筛选、状态、列表可扫读性
5. 最后再考虑局部视觉增强、图表、动效和质感

也就是说：

- 先产品结构
- 再设计系统
- 最后视觉表达

设计一个移动端“全部战报”页面，复刻网页端的筛选栏 + 高密度战报表格展示逻辑，但适配为移动端卡片式高密度列表。顶部有玩家名、同盟名、战斗结果、战斗类型、时间范围筛选和搜索按钮。每条战报展示时间、结果 badge、类型 badge、攻方、守方、武将摘要、wid 或关键位置和详情入口。不要沿用网页配色，但要保留其高密度、强结构、战术终端气质。
